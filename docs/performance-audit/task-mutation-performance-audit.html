Phase Task Mutation Performance Audit

Read-only audit · High-frequency superintendent task mutations · Generated from repository analysis · Do not modify code based on this document alone without an implementation plan

Scope: Complete, Start, Mark N/A, Schedule, Reschedule.

Not in scope: code changes, Transaction Engine migrations, caching, optimistic UI implementation.

Verdict: READY TO OPTIMIZE

1. Executive Summary

Superintendent task mutations in Phase are legacy online REST → Prisma paths. None of the five audited workflows use the Transaction Engine (only punch-item create does).

The dominant perceived-latency pattern on House Details:

  1. User waits for the mutation API before most UI updates (inline complete is post-response, not true optimistic).
  2. Every successful mutation triggers GET /api/homes/[id]/forecast, which recomputes CPM, persists forecast fields on every task, and returns the full home + all tasks payload.
  3. Gates are refetched in parallel (GET /api/homes/[id]/gates), loading all home tasks again and running N punch counts.
  4. setHome(fullHome) rerenders the entire ~1,250-line HomeDetailPage, including every category accordion and every work-item card.

Heaviest server paths: Schedule (duplicate full-home task loads for guards), Mark N/A (forecast persist on server plus client forecast refetch), Reschedule with SMS (Twilio in-request).

Best existing pattern: Inline complete applies a local task patch immediately after PATCH returns, then background-refetches forecast/gates — but the button still shows “Saving…” until PATCH completes.

7. Auth / Tenant Cost

Every mutation calls requireTenantContext():

  • getServerSession(authOptions)
  • Usually prisma.user.findUnique (+ company name)
  • Impersonation path may add lookup

Then hasPermission(role, "tasks:write") — in-memory, cheap. Forecast refetch uses requireTenantPermission("homes:read") — session + user again + superintendent assignment check. No per-request caching of tenant context. Redundant but likely small vs forecast/gates.

16. Recommended Optimization Sequence

Phase P1 — Client refetch/rerender (safest wins)

  • Patch local home.tasks from mutation response; stop awaiting forecast for status display
  • Defer /forecast and /gates (idle / background, coalesce rapid mutations)
  • Remove duplicate forecast on N/A (server OR client, not both)
  • Narrow rerender: split task list state or memoize rows carefully

Phase P2 — True optimistic UI

  • Complete/start: apply status on tap; rollback on 409/400
  • Keep dependency errors as server source of truth

Phase P3 — Server critical path

  • Move audit/activity/recalc to async jobs or waitUntil
  • Collapse schedule guard reads (single task load)
  • Slim PATCH response (TaskMutationResult DTO)

Phase P4 — Transaction Engine for status mutations

  • Complete/start/N/A first (highest frequency)

Phase P5 — Schedule/reschedule

  • Outbox SMS; optional optimistic date with server validation

18. Risks / Correctness Guardrails

Do not optimize away without replacement:

  • Tenant scoping on every mutation
  • Dependency guard (409 DEPENDENCY_BLOCKED)
  • Category/punch gate checks on schedule/reschedule
  • Reschedule history immutability
  • Confirmed → Scheduled demotion on reschedule
  • Contractor confirmation / SMS semantics
  • Audit/activity (can defer, not drop)
  • Forecast accuracy for portfolio/Dashboard (eventual consistency OK if labeled)

Risky ideas: optimistic schedule without gate revalidation; skipping forecast forever; caching tenant context across users; batching mutations without version checks.

19. First Optimization to Implement

Defer and coalesce post-mutation /forecast + /gates refetches; patch task state immediately from the mutation response.

  1. On PATCH/POST success, merge returned task into home.tasks (all entry points).
  2. Fire /forecast + /gates in background; debounce if superintendent taps multiple tasks quickly.
  3. For N/A, remove client forecast refetch (server already persists) or remove server persist from POST — pick one.
  4. Add lightweight performance.mark for tap→patch→reconcile when implementing.

Final Status

READY TO OPTIMIZE

No fundamental architectural flaw blocks incremental performance work. The main issue is synchronous request chains and full-home reconciliation, not missing indexes or Transaction Engine absence (yet).

Target experience (evaluation only — not implemented): Tap → visible UI <100ms; durable local acceptance <150ms where TE applies; normal server acknowledgement ideally <500ms; user blocked waiting as close to 0ms as safely possible.
